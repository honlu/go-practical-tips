## 性能

### 预分配切片容量以提升性能

以前我习惯用类似 `make([]int, 10)` 的方式来预分配切片，后来才意识到一个常见的误区：
虽然我预分配了切片，但仍然习惯性地用 `append()` 来追加元素，结果导致切片前面充满了默认值（0），这不是我想要的数据。

举个例子说明问题：

<table>
<thead><tr><th>Bad</th><th>Good</th></tr></thead>
<tbody>
<tr><td>

```go
a := make([]int, 5) // 长度为5，容量为5
a = append(a, 1) // [0 0 0 0 0 1]
```

</td><td>

```go
b := make([]int, 0, 5) // 长度为0，容量为5
b = append(b, 1) // [1]
```

</td></tr>
</tbody></table>

在第一个示例中，我在实际数据之前得到了一段全是 0 的切片，这效率不仅效率低，还可能在逻辑上产生错误。为了避免这种情况，最好使用 `make(a, 0, 10)`。  

当向切片追加一个元素时，如果长度超出了切片的容量，会发生什么？这时 Go 会进行一些复杂的操作来 “重新调整” 切片：

1. 首先，它会计算切片原长度以及要添加的新元素数量。

2. 然后，决定新的容量。如果切片较小，它可能会直接将当前容量翻倍。对于较大的切片，增长幅度会变小，避免浪费内存。

3. 确定新容量后，它会为这个调整后的切片分配内存。

4. 如果切片元素中有指针，Go 会采取额外步骤正确处理内存以保持数据完整性，即确保不会触发GC的错误引用。

5. 接下来，复制原切片数据元素到新内存位置，确保内容保持完整。

6. 最后，该函数会返回一个具有调整后长度和容量的新切片（注意：是新对象！旧切片不变）。

那么，这里的故事有什么启示呢？

> 只要你能预测需要多少空间，就提前为切片分配内存。

- 推荐做法：make([]T, 0, 预计容量)  
    这样可以控制内存分配，又不会导致前面出现零值占位。
- 为什么这重要：
    - 少走扩容逻辑，减少内存分配次数。
    - 提高性能，尤其在大量数据操作时更明显。
    - 防止逻辑错误（比如前面多出一堆 0）。

### 优先使用 `strconv` 而不是 `fmt` 进行字符串转换

在 Go 语言中，将数字转换为字符串时，选择合适的工具对性能影响显著。你可能会考虑使用 `fmt.Sprint`，但让我们来探讨为何 `strconv` 可能是完成此任务的更佳选择。

`strconv` 包专为字符串转换而设计，这意味着它针对将数字转换为字符串等任务进行了优化。在处理大规模应用程序时，每一点性能提升和内存节省都至关重要。

为了让你更清楚地了解，让我们看看 `fmt` 和 `strconv` 之间的简单基准测试比较：

```go
func BenchmarkFmt(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = fmt.Sprint(i)
    }
}

func BenchmarkStrconv(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = strconv.Itoa(i)
    }
}
```

当我们运行这些基准测试时，看看性能差异：

```shell
BenchmarkFmt-8      23821753    50.17 ns/op    16 B/op  2 allocs/op
BenchmarkStrconv-8  100000000   11.47 ns/op     3 B/op  1 allocs/op
```

_(不确定编译器是否进行了任何优化，但两者的上下文是相同的)_

如您所见，`strconv.Itoa` 在内存分配方面比 `fmt.Sprint` 显著更快且更高效，但这是为什么呢？

- `strconv.Itoa(..)` 专门设计用于将整数转换为字符串，这种专业化使其比更通用的 `fmt` 函数执行得更快。
- 另一方面，`fmt.Sprint` 及其变体需要进行一些额外的工作，它们使用反射来理解正在处理的数据类型，并确定将其格式化为字符串的最佳方式。

```go
func (p *pp) doPrint(a []any) {
	prevString := false
	for argNum, arg := range a {
+		isString := arg != nil && reflect.TypeOf(arg).Kind() == reflect.String
		...
+		p.printArg(arg, 'v') 
		...
	}
}
```

这个反射过程并非免开销的，它会增加时间和内存开销，当处理大量数据或需要高性能时，这些开销可能会相当显著。

### 按从大到小的顺序排序结构体中的字段

Go 结构体中字段的排序方式看似是一个小问题，但实际上对程序的内存使用有显著影响，尤其是在我们所说的“热点路径”中对性能至关重要。

以下是一个示例，我们比较了两个结构体定义，`A` 和 `OptimizedA`。

```go
// 32 bytes
type A struct {
    A byte 
    B int32
    C byte
    D int64
    E byte
}

// 16 bytes
type OptimizedA struct {
    D int64
    B int32
    A byte
    C byte
    E byte
}
```

`A` 结构体总共占用 32 字节，但 `OptimizedA` 将其减少到仅 16 字节，这种差异源于结构体内部字段的对齐方式和填充方式。

让我们进一步讲解这些概念：

- **对齐**：这指的是数据类型根据其大小具有特定的对齐要求。例如，一个 `int32` 可能需要对齐到 4 字节边界，这意味着其起始内存地址应能被 4 整除。
- **填充**：为了满足这些对齐要求，编译器通常会在结构体字段之间插入未使用空间（称为填充）。

为了更直观地理解，让我们看看A的内部布局，由于字段的对齐和填充方式，它实际上变成了8×4字节：

<div align="center">

| 0   | 1   | 2   | 3   | 4   | 5   | 6   | 7   |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A   |     |     |     | B   | B   | B   | B   |
| C   |     |     |     |     |     |     |     |
| D   | D   | D   | D   | D   | D   | D   | D   |
| E   |     |     |     |     |     |     |     |

</div>

- `A (byte)`：占用 1 个字节，但由于下一个字段 B 需要 4 字节对齐，因此在 A 之后添加了 3 个字节的填充以正确对齐 B。
- `B (int32)`：直接在填充之后占用 4 个字节，完美地落在 4 字节边界上。
- `C（byte）`：占用 1 个字节，但为了对齐需要 8 字节对齐的 D，在 C 之后添加了 7 个字节的填充。
- `D（int64）`：该字段需要 8 个字节，它完美地嵌入其位置，无需在其后添加额外填充。
- `E (byte)`：这是最后一个字节，紧跟在 D 之后。根据结构体整体对齐需求，末尾可能添加额外填充以将整个结构体大小对齐到边界。

`OptimizedA` 中字段的结构设计在内存效率方面相当巧妙。

<div align="center">

| 0   | 1   | 2   | 3   | 4   | 5   | 6   | 7   |
| --- | --- | --- | --- | --- | --- | --- | --- |
| D   | D   | D   | D   | D   | D   | D   | D   |
| B   | B   | B   | B   | A   | C   | E   |     |

</div>

在``OptimizedA`内存配置中：

- `D（int64）`：位于最前面。此方案消除了对前置填充的需求，这种填充通常只是占用空间而无实际意义。
- `B（int32）`：紧随其后，位于4字节边界上，这在D之后自然形成。
- `A、C、E（byte）`：这些单字节类型被分组在一起。由于这些是字节类型，它们可以紧密排列，无需在它们之间添加额外的填充。

我们在这里看到的是从最大到最小的字段的战略排序，这不仅仅是为了整洁，而是一项经过计算的举措，旨在最小化填充。

较少的填充意味着结构体的总大小减少，这反过来意味着它占用的内存更少。

有一个工具[betteralign](https://github.com/dkorunic/betteralign)，非常擅长发现这类字段对齐的低效问题。它甚至自动提供建议，重新排列字段以提升内存效率。

然而，需要记住，为了效率而重新排列字段**并不总是正确的选择**。

有时，保持一种映射字段使用方式或在程序整体上下文中重要性的顺序更有意义。这可以使代码更直观且易于维护，即使从内存占用角度来看，它可能不是最紧凑的格式。

> 可以当做一种内容优化参考，并不强求。
