## 性能

### 预分配切片容量以提升性能

以前我习惯用类似 `make([]int, 10)` 的方式来预分配切片，后来才意识到一个常见的误区：
虽然我预分配了切片，但仍然习惯性地用 `append()` 来追加元素，结果导致切片前面充满了默认值（0），这不是我想要的数据。

举个例子说明问题：

<table>
<thead><tr><th>Bad</th><th>Good</th></tr></thead>
<tbody>
<tr><td>

```go
a := make([]int, 5) // 长度为5，容量为5
a = append(a, 1) // [0 0 0 0 0 1]
```

</td><td>

```go
b := make([]int, 0, 5) // 长度为0，容量为5
b = append(b, 1) // [1]
```

</td></tr>
</tbody></table>

在第一个示例中，我在实际数据之前得到了一段全是 0 的切片，这效率不仅效率低，还可能在逻辑上产生错误。为了避免这种情况，最好使用 `make(a, 0, 10)`。  

当向切片追加一个元素时，如果长度超出了切片的容量，会发生什么？这时 Go 会进行一些复杂的操作来 “重新调整” 切片：

1. 首先，它会计算切片原长度以及要添加的新元素数量。

2. 然后，决定新的容量。如果切片较小，它可能会直接将当前容量翻倍。对于较大的切片，增长幅度会变小，避免浪费内存。

3. 确定新容量后，它会为这个调整后的切片分配内存。

4. 如果切片元素中有指针，Go 会采取额外步骤正确处理内存以保持数据完整性，即确保不会触发GC的错误引用。

5. 接下来，复制原切片数据元素到新内存位置，确保内容保持完整。

6. 最后，该函数会返回一个具有调整后长度和容量的新切片（注意：是新对象！旧切片不变）。

那么，这里的故事有什么启示呢？

> 只要你能预测需要多少空间，就提前为切片分配内存。

- 推荐做法：make([]T, 0, 预计容量)  
    这样可以控制内存分配，又不会导致前面出现零值占位。
- 为什么这重要：
    - 少走扩容逻辑，减少内存分配次数。
    - 提高性能，尤其在大量数据操作时更明显。
    - 防止逻辑错误（比如前面多出一堆 0）。

### 优先使用 `strconv` 而不是 `fmt` 进行字符串转换

在 Go 语言中，将数字转换为字符串时，选择合适的工具对性能影响显著。你可能会考虑使用 `fmt.Sprint`，但让我们来探讨为何 `strconv` 可能是完成此任务的更佳选择。

`strconv` 包专为字符串转换而设计，这意味着它针对将数字转换为字符串等任务进行了优化。在处理大规模应用程序时，每一点性能提升和内存节省都至关重要。

为了让你更清楚地了解，让我们看看 `fmt` 和 `strconv` 之间的简单基准测试比较：

```go
func BenchmarkFmt(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = fmt.Sprint(i)
    }
}

func BenchmarkStrconv(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = strconv.Itoa(i)
    }
}
```

当我们运行这些基准测试时，看看性能差异：

```shell
BenchmarkFmt-8      23821753    50.17 ns/op    16 B/op  2 allocs/op
BenchmarkStrconv-8  100000000   11.47 ns/op     3 B/op  1 allocs/op
```

_(不确定编译器是否进行了任何优化，但两者的上下文是相同的)_

如您所见，`strconv.Itoa` 在内存分配方面比 `fmt.Sprint` 显著更快且更高效，但这是为什么呢？

- `strconv.Itoa(..)` 专门设计用于将整数转换为字符串，这种专业化使其比更通用的 `fmt` 函数执行得更快。
- 另一方面，`fmt.Sprint` 及其变体需要进行一些额外的工作，它们使用反射来理解正在处理的数据类型，并确定将其格式化为字符串的最佳方式。

```go
func (p *pp) doPrint(a []any) {
	prevString := false
	for argNum, arg := range a {
+		isString := arg != nil && reflect.TypeOf(arg).Kind() == reflect.String
		...
+		p.printArg(arg, 'v') 
		...
	}
}
```

这个反射过程并非免开销的，它会增加时间和内存开销，当处理大量数据或需要高性能时，这些开销可能会相当显著。
